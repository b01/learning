# Initialize the Control Plane

It SHOULD be noted that, if the components run as container in the cluster, it
is the `kubelet` that is solely responsible for starting the cluster and
ensuring its components keep running.

NOTE: When the cluster starts, the `kubelet` will use
[Token authentication file] to connect to the `kube-apisever`. After cluster
initialization, we'll immediately switch to [Bootstrap Tokens]. We prefer to use
bootstrap tokens but cannot start with this because they are stored as secrets
in the cluster. This is an egg before the chicken type of scenario since the
token has not been made or the bindings added to the cluster.
For reasons, Kubernetes ships with the role, but not the bindings. However,
once the cluster has started successfully, we will add them
using steps documented in [Bootstrap Tokens]. We'll also need to manually
approve a few CSRs. But after that adding any additional clusters should be
fully automated.

## Start Kubelet Service

Time to start the `kubelet` service on the control-plane which, in turn, it will
start the remaining control-plane components; using their manifests located in
`/etc/kubernetes/manifest` directory.

1. Make a configuration for the `kubelet` and place it in `/var/lib/kubelet`,
   using the [samples/config.yaml] in this repository.

   ```shell
   sudo mkdir -p /var/lib/kubelet
   sudo install -m 644 /vagrant/config.yaml /var/lib/kubelet
   ```

   NOTE: Options `rotateCertificates` and `serverTLSBootstrap` have been
   enabled. This ensures that a new and proper `kubelet` serving certificate
   will be generated, listing both hostnames and IPs in its SANs. When they are
   near expiration, the cluster can auto-renew them.
2. Make a `systemd` unit (kubelet.service), which tells the `kubelet`
   service where to find its configuration file and the kubeconfig for
   authenticating with the `kube-apiserver`.

   ```shell
   getIps () {
      iface=${1}
      export IPV4=$(ip -4 addr show scope global dev ${iface} | grep "inet\b" | awk '{print $2}' | cut -d/ -f1)
      export IPV6=$(ip -6 addr show scope global dev ${iface} | grep "inet6\b" | awk '{print $2}' | cut -d/ -f1)
   }
   getIps "enp0s8"
   sudo install -d /etc/systemd/system/kubelet.service.d
   cat /vagrant/kubelet.service.tmpl | envsubst | tee kubelet.conf
   sudo install -m 644 kubelet.conf /etc/systemd/system/kubelet.service.d/kubelet.conf
   ```

   NOTE: The `kubelet` options `--bootstrap-kubeconfig` and `--kubeconfig` are
   both REQUIRED, otherwise starting the `kubelet` will fail and exit
   immediately. Since our cluster is IPv6 primary, we also listed the IPv6 IP
   first. Just to keep things uniform, I've not seen any documentation that
   state this has any effect.
3. Start the cluster components.

   ```shell
   sudo systemctl daemon-reload
   sudo systemctl start kubelet.service
   ```
4. Then check the status of the components to make sure they started
   successfully.

   ```shell
   sudo systemctl status kubelet.service
   # check the components are running
   sudo crictl ps -a
   # Test etcd connection.
   sudo crictl exec -it $(crictl ps --name etcd -q) etcdctl --endpoints=https://[::1]:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key endpoint health
   ```
5. Mark the node as a control-plane by adding the following Label and Taint.
   The Taint will prevent Pods from being scheduled on the control-plane unless
   configured to do so; while the label distinguishes it from worker nodes.

   ```shell
   sudo kubectl label nodes control-plane-01 node-restriction.kubernetes.io/control-plane=true \
     --kubeconfig=/etc/kubernetes/super-admin.conf
   sudo kubectl taint nodes control-plane-01 control-plane:NoSchedule \
     --kubeconfig=/etc/kubernetes/super-admin.conf
   ```

   NOTE: We have not set a default kubeconfig for accessing the cluster at this
   point, which is why we have to specify one. Very useful when you need to try
   out a different config for any reason.

NOTE: If your having issues you can review the `kubelet` logs with
`sudo journalctl -u kubelet.service`.
