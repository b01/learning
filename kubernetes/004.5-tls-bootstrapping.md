# TLS bootstrapping

This process allows a `kubelet` authorization to authenticate with the
`kube-apiserver` then generate a long-term TLS certificate for itself.
It will also renew that certificate when its expiration time is near.

For more details see [kubelet TLS bootstrapping] and [Authenticating with
Bootstrap Tokens].

1. Add a default kubeconfig to access the cluster.

   ```shell
   mkdir -p ~/.kube
   sudo cp /etc/kubernetes/admin.conf ~/.kube/config
   sudo chown vagrant:vagrant ~/.kube/config
   chmod 0700 ~/.kube/config
   sudo kubectl create clusterrolebinding \
     kubernetes-admin --clusterrole=cluster-admin --user=kubernetes-admin \
     --kubeconfig /etc/kubernetes/super-admin.conf
   ```
2. Initial bootstrap authentication can be done with one of the following:
   1. Generate a Bootstrap token:

      ```shell
      TOKEN_ID=$(openssl rand -base64 10 | tr -dc 'a-z0-9' | head -c 6)
      TOKEN_SECRET=$(openssl rand -base64 10 | tr -dc 'a-z0-9' | head -c 16)
      cat <<TXT | envsubst | tee bootstrap-token.yaml | sudo kubectl apply --kubeconfig=/etc/kubernetes/super-admin.conf -f -
      apiVersion: v1
      kind: Secret
      metadata:
        name: bootstrap-token-${TOKEN_ID}
        namespace: kube-system
      type: bootstrap.kubernetes.io/token
      stringData:
        description: "The default bootstrap token generated manually."
        auth-extra-groups: system:bootstrappers:worker,system:bootstrappers:ingress
        token-id: "${TOKEN_ID}"
        token-secret: "${TOKEN_SECRET}"
        # Allowed usages.
        usage-bootstrap-authentication: "true"
        usage-bootstrap-signing: "true"
      TXT
      ```

      NOTE: The type of the secret must be `bootstrap.kubernetes.io/token` and
      the name must be `bootstrap-token-<token id>`. It must also exist in the
      `kube-system` namespace. Bootstrap Tokens must match the regular
      expression `[a-z0-9]{6}\.[a-z0-9]{16}`.
3. Enable bootstrapping nodes to make a CSR by adding this `ClusterRoleBinding`
   on the `control-plane-01`.

   ```shell
   cat <<TXT | sudo kubectl apply --kubeconfig=/etc/kubernetes/super-admin.conf -f -
   apiVersion: rbac.authorization.k8s.io/v1
   kind: ClusterRoleBinding
   metadata:
     name: create-csrs-for-bootstrapping
   subjects:
   - kind: Group
     name: system:bootstrappers
     apiGroup: rbac.authorization.k8s.io
   roleRef:
     kind: ClusterRole
     name: system:node-bootstrapper
     apiGroup: rbac.authorization.k8s.io
   TXT
   ```
4. In order to have the `controller-manager` auto-approve CSRs, you need to make
   ClusterRoleBindings that grant RBAC permissions to the correct group.
   There are two distinct sets of permissions:
   * `nodeclient`: When a node does not have a certificate, and wants to make a
     new one; while authenticating using one of the tokens listed above. Then
     it is part of the group `system:bootstrappers`.

     Apply this `ClusterRoleBinding`:

     ```shell
     # Auto approve new CSRs for the group "system:bootstrappers"
     cat <<TXT | sudo kubectl apply --kubeconfig=/etc/kubernetes/super-admin.conf -f -
     apiVersion: rbac.authorization.k8s.io/v1
     kind: ClusterRoleBinding
     metadata:
       name: auto-approve-csrs-for-group
     subjects:
     - kind: Group
       name: system:bootstrappers
       apiGroup: rbac.authorization.k8s.io
     roleRef:
       kind: ClusterRole
       name: system:certificates.k8s.io:certificatesigningrequests:nodeclient
       apiGroup: rbac.authorization.k8s.io
     TXT
     ```
   * `selfnodeclient`: When a node is renewing its certificate, then it already
     has a certificate (by definition), which it uses continuously to
     authenticate as part of the group `system:nodes`.

     To enable the `kubelet` to renew its own client certificate, apply this
     ClusterRoleBinding:

     ```shell
     # Auto approve renewal CSRs for the group "system:nodes"
     cat <<TXT | sudo kubectl apply --kubeconfig=/etc/kubernetes/super-admin.conf -f -
     apiVersion: rbac.authorization.k8s.io/v1
     kind: ClusterRoleBinding
     metadata:
       name: auto-approve-renewals-for-nodes
     subjects:
     - kind: Group
       name: system:nodes
       apiGroup: rbac.authorization.k8s.io
     roleRef:
       kind: ClusterRole
       name: system:certificates.k8s.io:certificatesigningrequests:selfnodeclient
       apiGroup: rbac.authorization.k8s.io
     TXT
     ```

     ```shell
     kubectl create clusterrolebinding system:certificates.k8s.io:certificatesigningrequests:node-server \
     --clusterrole=system:certificates.k8s.io:certificatesigningrequests:node-server \
     --group=system:nodes

     kubectl create clusterrolebinding system:certificates.k8s.io:certificatesigningrequests:selfnode-server \
     --clusterrole=system:certificates.k8s.io:certificatesigningrequests:selfnode-server \
     --group=system:nodes
     ```
     NOTE:
     The CSR approving controllers implemented in core Kubernetes do not approve
     node serving certificates for security reasons. To use
     RotateKubeletServerCertificate operators need to run a custom approving
     controller, or manually approve the serving certificate requests.
5. The `kubelet` will have generated a CSR to allow itself to generate its
   own certificate. Let's list those CSRs and manually approve them if you did
   not apply the auto-approving ClusterRoleBindings:

   ```shell
   kubectl get csr
   ```
   then approve with:

   ```shell
   kubectl certificate approve <csr-name>
   ```

   NOTE: This ensures that a new `kubelet` client certificate is issued. You
   may need to run it twice, if the options `rotateCertificates` and
   `serverTLSBootstrap` have been enabled in the `kubelet` configuration.
   Which will also generate a CSR for its server certificate generated with
   proper SANs. You can review it with:

   ```shell
   sudo openssl x509 -text -noout -in /var/lib/kubelet/pki/kubelet-server-current.pem
   ```
