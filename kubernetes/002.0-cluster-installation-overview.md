# Cluster Installation Overview

Here is where you'll choose to install a cluster manually or with the setup tool
`kubeadm`. Each has its own benefits.

## Manual Cluster Install

Get hands-on with each component of a cluster. You'll configure each
component and possibly gain a greater understanding of the overall cluster
architecture.

Manually deploying a Kubernetes cluster is very beneficial as it can:
1. Help you learn where all the components are, and their corresponding
   configurations are located.
2. You'll likely mess-it-up, which is good because now you'll have a cluster
   that you can practice troubleshooting; which can be a great learning boost.
3. Grant you more knowledge to compliment any courses you have taken.
4. Speed up your ability to resolve issues.
5. Give you detailed insights to aid in your journey as a CKA.

### Checklist

1. Preparing the machines for cluster installation, here you can use the
   [Local Virtual Environment] guide that will walk you through:
   1. Configuring kernel features and disabling swap space.
   2. [Install containerd] as the CRI of choice on all machines.
   3. Install a debug tool such a `crictl`.
   4. [Installing kubeadm, kubelet and kubectl] packages using the system
      package manager on all machines.
   5. Choose which IP CIDR ranges you want to use for IPv4 and/or IPv6 for the
      clusters' Pod and Service networks; or use the ranges provided.
2. [Generate Control Plane Certificates Manually] to set up cluster PKI.
3. [Generate Control Plane kubeconfigs Manually] for components and cluster
   admins.
4. [Generate Static Pod Manifests] for components:
   1. `etcd`
   2. `kube-apiserver`
   3. `kube-controller-manager`
   4. `kube-scheduler`
5. [Initialize the Control Plane] by starting the `kubelet` service on the
   `control-plane-01` node. Which read the manifests.
6. [Configure Networking] by deploying a CNI network addon.
7. [Add Workers] nodes to the cluster.

To take this path click the [Manual Cluster Install].

## kubeadm Cluster Install

`kubeadm` is a setup tool to reduce cluster installation steps. Automating the
tedious setup of PKI and components; simplifying adding nodes, and more.
It does a lot of the heavily lifting for initial deployment.

This tool is likely what you would use at a real job. `kubeadm` handles
the complexities of cluster installation. However, preparing the machines is
a separate task. This guide uses the same preparation as the manual cluster
install.

### Checklist

1. Preparing the machines for cluster installation, here you can use the
   [Local Virtual Environment] guide that will walk you through:
   1. Configuring kernel features and disabling swap space.
   2. [Install containerd] as the CRI of choice on all machines.
   3. Install a debug tool such a `crictl`.
   4. [Installing kubeadm, kubelet and kubectl] packages using the system
      package manager on all machines.
   5. Choose which IP CIDR ranges you want to use for IPv4 and/or IPv6 for the
      clusters' Pod and Service networks; or use the ranges provided.
2. Run `kubeadm init` with desired configuration to initialize component on the
   control-plane-01 machine.
3. [Installing Addons] (CNI compliant) to facilitate Pod Networking.
4. [Join Workers].

To take this path click the [kubeadm Cluster Install].

## Dual Stack

For either manual or tool assisted setups we will default to making the cluster
a Dual stack cluster.
In addition, you also have to decide if it will be IPv6 or IPv4 Primary. This
guide defaults to IPv6 Primary. Making this decision simply involves listing
either IPv6 or IPv4 family first and consistently across configurations.

In order to properly configure a cluster for dual-stack, here's what you
should know:
1. Select IPv6 and IPv4 CIDR blocks for both the Pod and Service Networks, for
   example, these are the CIDRs used in this guide:
   ```text
   IPv4 POD network:     10.244.0.0/16
   IPv4 Service Network: 10.96.0.0/16
   IPv6 POD network:     fd12:3456:789a:1000::/56
   IPv6 Service network: fd12:3456:789a:2000::/112
   ```
2. Decide if you want to make IPv6 Primary cluster, meaning it defaults to use
   IPv6 addresses. This is done by setting the IPv6 address before the
   IPv4 address in any comma separated strings or YAML arrays.
3. Make sure to set both IPv6 and IPv4 CIDR blocks in any configuration where
   needed, for example in te `kubeadm` init configuration, again setting the
   IPv6 address first when you want to make it Primary. For example:
   ```yaml
   # excerpt from sample init config, dual-stack with IPv6 Primary
   networking:
     podSubnet: fd12:3456:789a:1000::/56,10.244.0.0/16
     serviceSubnet: fd12:3456:789a:2000::/112,10.96.0.0/16
   ```
4. You MUST also inject both IPv6 and IPv4 addresses into the `kubelet`
   configuration either in the environment variable
   `KUBELET_EXTRA_ARGS`, `--node-ip` flag, or directly in a configuration file
   you use. Here's how you'd set them in the environment variable, again make
   note of the order if you want an IPv6 Primary cluster:
   ```shell
   KUBELET_EXTRA_ARGS="--node-ip=2000:192:168:56::11,192.168.56.11"
   ```
   You can use the [generate-kubelet-extra-args.sh] script during your install
   to set the `KUBELET_EXTRA_ARGS` environment variable so that your kubelet
   gets the correct IPs. Note this script is intended for an IPv6 Primary
   cluster.
5. Your services can also make use of dual-stack. Review this
   [dual-stack-preferred-svc.yaml] configuration for how.
6. You can set `advertiseAddress` to the nodes adapter's IPv6 address. As an
   IPv4 will leave it in IPv4 mode only.
   ```yaml
   ---
   apiVersion: kubeadm.k8s.io/v1beta4
   kind: InitConfiguration
   localAPIEndpoint:
     advertiseAddress: <set-IPv6-address>
   ```
7. Use the Kubernetes documented process to [Validate IPv4/IPv6 dual-stack]
   clusters.

## Cluster Install on AWS Overview

We now turn to setting up a `self-hosted` Kubernetes (without EKS) cluster in
AWS. We'll use kubeadm, although this can be done with the manual process as
well, we want to save time which will also save money.

That's right, this will cost us money. Somewhere around $5-20 US dollars
depending on how much time we take. The $20 bucks is worst case, which can
be 7+ days, even with the Nat Gateway and 3 EC2 instances we'll need.
Just remember to shut down the EC2 instance and delete the NAT Gateway when you
take long breaks. Spinning them up is fairly fast.

### Checklist

1. Make an EC2 instance Launch template, which is free.
2. Deploy a VPC with 4 subnets, 2 public and 2 private, make it Dual Stack.
